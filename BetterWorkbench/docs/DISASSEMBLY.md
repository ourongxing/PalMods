# 即时分解（已接入 Lua 候选版本，游戏验收待完成）

需求：选中工作台条目后，点击详情区右上角原有的已有成品数量，切换生产／分解模式，不显示单独的模式按钮；只有库存够一批时允许进入分解。确认后立即消耗成品，把所选配方的原始材料全额返还到当前玩家背包。不排生产任务，不需要工作量。小条目不新增数量按钮。

## 已实现的核心

`DisassemblyPlan.resolve` 按明确选中的配方 ID 反向计算，不猜测同物品的其他配方。原始材料全额返还，不递归展开中间材料，不应用制作研究减耗。每批消耗 `OutputAmount` 个成品，返还一份 `Materials`；不进行小数返还。例如每批产出两个成品的配方，已有七个时最多分解三批，保留一个成品。

计划包含已有数量、最大批数、成品投入、材料返还清单和零工作量。当前工作台范围、分解资格、成品库存、数量上限都须验证；计算不修改输入数据。

`CraftService.previewDisassembly` 使用独立的分解库存快照；`CraftService.disassemble` 要求后端在事务内重新读取配方、权限和库存。提交只接受配方 ID 与批数，不接受客户端返还清单。没有原生后端时返回 `native_disassembly_unavailable`。

## 游戏接入与使用

`DisassemblyRuntime` 提供独立的分解后端，不依赖制作 DLL 的任务接口。实现参考本机正常工作的 AntiWasteDisassembleItems 2.3.3：调用玩家库存的 `AddItem_ServerInternal` 返还原始材料，再减少成品槽的 `StackCount`，最后触发槽更新。没有修改参考 Mod。

`DisassemblyUI` 在详情区的 `CanvasPanel_ItemNum` 内添加透明点击区域，保留原有数量和布局，并移除旧的独立“生产／分解”按钮。数量不足一批时禁止进入分解，点击时重新核对当前条目和库存，防止过期状态进入分解。直接复用原生产界面的数量选择器、材料列表和确认按钮，工作量显示零。分解模式下再次点击已有数量切回生产，即使成品已耗尽也允许切回；选择其他条目也退出分解。关闭工作台后清理会话；无轮询、无全世界实例遍历。热更新时清理旧版本误加在小条目上的按钮并恢复配方产出数量。

入口在计数画布内横向拉伸，左右偏移为零；外层高度固定为 28，垂直居中，关闭槽位自动尺寸。焦点框可能使用外层控件范围，因此同时约束外层尺寸，而非仅缩小内部点击按钮。通用按钮文字为空、渲染透明，折叠内部装饰和文字，仅保留隐形点击按钮，并清除其四边外扩边距，使焦点框贴合原计数区域。保留点击检测及原有输入与焦点行为，不额外显示模式文字或 tooltip。

手柄直接通过左摇杆焦点导航到入口，使用原生确认键点击，不新增快捷键。先修复进入具体条目的焦点交接：入口和原确认按钮内部的 `WBP_PalInvisibleButton` 开启可聚焦、默认确认动作及焦点光标。实际手柄选中条目后，显式把用户焦点交给可用的确认按钮；确认禁用时优先交给可用的分解入口，均不可用时保留数量区域焦点。该交接不再以“此前已有焦点”为条件。启动补挂及分解后的原生库存刷新不执行额外焦点交接，鼠标选择不抢焦点。

配方列表向右的边界通往入口，入口向左回到所选配方、向下回到确认按钮，确认按钮向上回到入口。工作台原本在数量选择时禁用全部导航，`InputMethodChanged` 后置钩子仅恢复摇杆导航，十字键仍用于原有数量操作；记录输入类型以处理原生事件早于入口创建的情况。鼠标／键盘切换沿用游戏原设置。离线测试覆盖了无初始焦点时的交接和鼠标不抢焦点；实际手柄移动和确认仍待用户验证。

分解模式为当前 UI 模型的 `CanStartProduction` 原生返回值覆盖为非成功值 `1`，阻止原 `StartProduce` 创建生产任务；其 Blueprint 后置钩子改为调用分解后端。该路径同时覆盖原生产按钮和手柄绑定。进入分解模式前实际调用 `CanStartProduction` 确认保护生效，失败则退出模式。材料刷新钩子保持返还预览，数量始终限制在当前成品整批库存与 256 批以内。

右上角复用游戏原来的已有数量，不在切换模式时覆盖。分解后通过原 `OnClickedRecipeSlot` 刷新库存显示，刷新期间不退出分解模式。标题的 `BP_PalTextBlock_Num` 固定显示每批成品数量，不随选择的批数变化。按钮显示“开始分解”。`nowNum` 表示批数，`GroupCount` 用于数量显示。

成功分解不显示弹窗，实际消耗及返还数量仅记录到日志，材料加入背包的原生系统提示继续保留。失败仍使用游戏的 `PalUtility:Alert` 显示背包空间不足、库存不足或已停止分解等原因。通知失败只记录日志，不重试分解。离线 UI 测试核对了成功时无弹窗、失败提示及失败时库存不变。

每种返还材料的 `AddItem_ServerInternal` 调用开启 `bNotifyLog=true`，触发游戏原生获得物品／加入背包提示，数量使用实际返还量。此系统提示与分解结果反馈同时保留；不为了显示通知再次添加物品。

数量选择保留原选择并限制到剩余整批库存。没有成品时，上限和选择均为 0、清空返还预览并禁用确认；手柄确认也拒绝零数量。成品来源包括背包和当前工作台所属基地的库存模块，容器去重；使用生产界面的 `CollectLocalPlayerControllableItemInfos(..., 2)` 核对可用成品总数，来源数量不一致时在写入前拒绝。2026-10-07 00:05 游戏只读核对确认电脑成品总数 30，与截图生产计数一致；实际基地扣除及保存读档仍待游戏验收。

当前约束：

- 仅单人／房主本机，客户端和专用服务器远程玩家未实现请求协议。
- 成品先从玩家库存扣除，再从当前工作台基地的已解析容器扣除；可用总数必须匹配生产统计。未解析或受限容器导致数量不一致时拒绝。按静态物品 ID、槽顺序取整批成品，不能选择同 ID 的特定品质／耐久物品；每件按原配方全额返还。
- 最多一次 256 批。返还材料须为普通可堆叠物品，要求能读到原生目标容器和最大堆叠数；未知信息直接拒绝。
- 先为所有返还材料共同试算槽位容量，再调用原生添加；由于先返还再扣成品，尚未扣除的成品槽不计作空位。背包不足时不写入。
- 每次确认重新读取当前配方、工作台范围和成品数量。核对添加后的库存和最终库存；发现写入异常则尝试恢复原槽数量，并禁用本次运行的后续分解。
- 这不是原生原子事务。原生添加仍可能受过滤器等游戏条件影响，失败时可能掉落到世界；背包数量回滚无法撤销世界掉落。因此异常后禁用重试，实际游戏容量、动态装备和存档持久化仍需要验收。

## 2026-10-06 原生接口核实

23:00 和 23:03 在运行中的游戏进行了两次一次性只读反射检查。`DisassemblyProbe` 仅检查明确指定的原生类、函数和参数定义，不遍历实例或库存，不注册库存钩子，不调用添加／消耗接口。临时启动代码已从部署的 `main.lua` 撤回，原文件哈希一致；检查后游戏进程仍在运行。原始证据保存在本机 `.tools/disassembly-schema.log` 和 `.tools/disassembly-schema-operations.log`。

| 实际所属对象与函数 | 已确认参数顺序 | 返回 |
| --- | --- | --- |
| `PalPlayerInventoryData:AddItem_ServerInternal` | `StaticItemId` (Name), `Count` (Int), `IsAssignPassive` (Bool), `LogDelay` (Float), `bNotifyLog` (Bool) | Enum |
| `PalNetworkPlayerComponent:RequestAddItem_ToServer` | `StaticItemId` (Name), `Count` (Int), `IsAssignPassive` (Bool) | 无返回参数 |
| `PalPlayerInventoryData:TryGetContainerIdFromItemType` | `ItemTypeA` (Enum), `OutContainerId` (`PalContainerId`) | Bool |
| `PalNetworkPlayerComponent:RequestMoveItemToInventoryFromContainer` | `fromContainer` (Object), `IsTryEquip` (Bool) | 无返回参数 |

上层添加函数仍只能接收一种静态物品。`AddItem_ServerInternal` 的 exec 调用 `0x317b260`，后者调用 `0x317abc0`；下层添加结果非成功时还有另一条处理路径，最后返回值并不直接保留该下层结果。不能把上层 Enum 返回当作“全部物品已经放入背包”的证明。

进一步静态定位到以下候选路径（只进行了反汇编／反编译，未在游戏内调用）：

- `0x2fbc7c0`：单种添加到目标容器的包装，调用准备函数，再按结果执行写入。
- `0x2fc0ff0`：目标容器、添加列表和移除列表共用的准备路径；移除准备先于添加检查。
- `0x2fc1400`：在同一次准备中接受添加列表与移除列表，添加记录按 `0x58` 步长遍历，先验证输入及目标槽，生成操作清单。
- `0x2fb5680`：由包装函数在准备结果允许时调用，实际应用操作清单，并触发容器更新。

这些原生候选未被当前 Lua 实现调用。其调用约定、完整记录字段和失败清理仍未核实，不能据此宣称原生原子事务已实现。
