# Palworld Mod 开发 SOP

本仓库新增、修改、调试 mod 的默认流程。用户说“直接写 mod”“开始做”时，即按本流程完成研究、实现、本地安装、实机验证和交付，不停在方案或代码能运行这一层。已有授权内的常规步骤直接继续；关键需求确实缺失时先问清，同时推进不依赖答案的工作。

本流程来自 Better Arena 的完整开发与修复。通用要求适用于 Lua、PalSchema、cooked 资源和原生 C++ mod；具体接口与安装布局按对应 mod 调整。

## 1. 先确定玩家最终要完成什么

从本轮和此前已确认的要求整理一份简短的行为清单，写入 mod 的 README 或实现说明：

- 入口在哪里、点击几层、每一步显示什么、最终发生什么。
- 解锁条件、次数或消耗、刷新时钟、共享范围，以及升级、退出、重启后的行为。
- 奖励、积分等读取游戏当前规则，还是明确使用独立规则。
- 支持单机、房主、联机客户端、专用服务器中的哪些环境。
- 保留哪些原版行为，和已有 mod 的兼容边界是什么。

以用户最后确认的需求为准。设计变化后同步更新代码、测试、README 和验收说明，不保留已经过时的主流程描述。

Better Arena 最终需求示例：竞技场主菜单新增“扫荡”→ 原生样式的难度页 → 点击任一已通关难度立即领取该档重复奖励和胜利积分；玩家积分段位决定每日共享次数；成功后有到账动画、音效和实际奖励明细。挑战段位、玩家积分段位、积分数值是不同概念，不能互相代用。

## 2. 建立环境基线，识别真正生效的内容

1. 读取根目录和目标目录的 `AGENTS.md`，查看 Git 状态、当前分支和现有工具约定；保留无关的本地修改。
2. 确认游戏路径、游戏版本、UE4SS／SDK 版本，以及实际加载的安装目录和日志路径。
3. 检查相关 mod 是否仍通过本地文件、Workshop 文件、托管安装清单或加载列表生效。订阅状态和实际加载状态分别核对。
4. 如需研究已安装 mod，先确认它包含源码、配置还是 cooked 二进制；解包得到的资源／反编译结果不能称为原始源码。
5. 删除、卸载其他 mod 需要用户明确授权；有授权后备份对应文件，检查全部实际安装入口，完成后验证它已不再生效。

研究临时文件、反射结果、资源解包、日志、存档副本和截图统一放在 `.build/<任务>/`；外部工具和依赖按仓库已有方式管理，不把临时工具、游戏资源或存档混入提交。

本机常见路径，仅作定位起点，每次确认实际配置：

| 内容 | 常见位置 |
| --- | --- |
| 游戏目录 | `G:/SteamLibrary/steamapps/common/Palworld/` |
| 本地 UE4SS mod | `<游戏目录>/Mods/NativeMods/UE4SS/Mods/` |
| UE4SS 日志 | `<游戏目录>/Mods/NativeMods/UE4SS/UE4SS.log` |
| 存档和 mod 持久数据 | `%LOCALAPPDATA%/Pal/Saved/` |
| Workshop 安装 | `G:/SteamLibrary/steamapps/workshop/content/1623730/<PublishedId>/` |

## 3. 研究原生调用链，再选实现方式

优先使用现有工具和最小范围的只读研究：配置／数据表 → 原生 UI 和蓝图调用 → 反射接口 → 必要的二进制分析。选择能完成需求且容易验证的实现方式；Lua 不够时才增加对应原生桥接或资源修改。

已安装 PalSchema 且需求只是修改数据表或蓝图默认值时，优先用 `raw/`、`blueprints/` 补丁；已有 Lua 界面不代表数据也必须在 Lua 中修改。玩家配置可离线生成，或在用户明确要求时由 mod 启动后生成自有 JSON，使用 PalSchema 官方热重载应用；记录原版数据版本、依赖和覆盖范围。不要为单纯改数值增加运行中的原生表遍历、结构体缓存和定时写入。

自动生成方案须确认文件监听已开启、目标资源已加载、修改事件确实触发，并以实际值校验成功后再开放结算。PalSchema 的蓝图热重载按完整资源路径修改默认对象，不代表既有实例已更新。生成文件由游戏线程完整写入并关闭后，PalSchema 在游戏线程解析；不能假定重命名会触发只监听 Add／Modified 的加载器。本例经用户明确授权的自有 PalSchema 数据生成不等同于修改运行中的 Lua／DLL／PAK；代码、探针和其他运行资源安装仍必须退出游戏。

为关键功能确认以下证据：

- 真实类名、函数签名、枚举值、结构字段、调用线程和权威端要求。
- UI 的创建、打开、关闭、初始化时机，以及点击、悬停、返回和结算的实际路径。
- 参数来源、奖励概率、数量范围、积分倍率、取整方式、存档字段和通知机制。
- 哪些控件是绑定字段，哪些必须在控件树中查找；遍历须限定范围。

接口存在不代表 Shipping 构建真正执行。通过调用前后实际状态验证写入效果；不要只凭函数名、没有抛错或 Debug 接口的返回就宣告成功。原生结构可能含锁和不可复制成员，避免把未经确认的外层结构通过 Lua 按值传递；先读取必要的反射标量或数组。

探针必须范围有限、可移除、不改变奖励或存档。探针也按第 7 节关闭游戏后安装，禁止通过修改运行中脚本来注入。

## 4. 将规则、结算和游戏接口分开

沿用目标 mod 的现有结构。新功能可参考 Better Arena 的分层，但不要求每个简单 mod 都复制全部模块：

| 层 | 职责 |
| --- | --- |
| 规则／配置 | 次数、概率、积分计算、边界检查；可脱离游戏验证 |
| Runtime | 读取当前游戏状态、检查容量、执行原生操作 |
| Service | 校验条件、控制重入、持久化与结算顺序 |
| Store | 世界／玩家隔离、数据格式、读写失败与恢复策略 |
| UI／Feedback | 入口、显示、事件绑定、反馈和生命周期清理 |

游戏对象访问、UI 修改和结算在游戏线程执行；异步定时器只调度工作。防止重复排队、快速双击、回调重入和重复注册，限制轮询和诊断输出。

修改物品、积分、消耗等状态时：

1. 在实际执行时重新校验世界、人物、权限、解锁条件、额度和背包空间；UI 状态不能作为唯一授权依据。
2. 使用游戏生效中的奖励和设置，记录真实抽取结果，不按预览上限或假定常数发放。
3. 校验成功后再进行结算。涉及独立持久数据时明确预留、完成、异常中断的顺序，阻止不确定结算的自动重放。
4. 世界和玩家身份采用稳定标识，不能用角色名或只用当前菜单区分；按需求明确游戏日／现实日、跨天、升段和时钟回退策略。
5. 数据损坏、磁盘失败、部分发奖或背包不足不能变成免费重试。说明游戏存档与 mod 独立记录的回档边界。

Better Arena 的预留日志策略是具体参考，不是所有游戏操作的通用原子事务；按真实调用能力设计，并如实记录无法保证的部分。

## 5. UI 必须完成整个交互和反馈

尽量复用游戏已有控件、字体、布局、悬停预览、动画和音效。用户给出入口位置时，先实现对应层级，不能用另一个方便的按钮代替。

- 新功能只接管自己的入口和页面。改绑委托前保存原绑定，关闭时恢复；原版挑战等其他路径保持正常。
- 控件由有效父级或明确生命周期持有；返回、隐藏、地图切换时清理代理控件、横幅和会话引用。
- 锁定、零次数、读取失败、背包满和处理中，都需要可理解的显示，且能返回。
- 不能假定 `SetIsEnabled(false)` 是无害的视觉禁用；须实测原生材质、焦点、导航和悬停。Better Arena 的整个卡片禁用会显示白块，最终采用降低亮度、显示原因和点击拦截。
- 点击结算成功后给出明确到账反馈：实际道具与数量、实际积分变化，配合适当动画／音效；不能只悄悄改变背包或次数。
- 到账反馈以已完成的结算结果为依据，失败不播放成功效果。反馈失败不能重发奖励或把已成功领取重新执行。
- 非交互提示不能抢焦点或挡住按钮；重复领取、自动收起、提示中返回都要正确清理。
- 新文案按 mod 的语言支持范围维护，不把调试文本或内部错误原样显示给玩家。

## 6. 离线检查和打包

优先验证有风险的规则、状态变化和集成边界；不为纯样式小改机械增加镜像实现的测试。

涉及结算和 UI 接管时，至少覆盖相应的条件校验、正常结算、双击／重入、异常中断、数据隔离、边界状态和委托恢复。新增 mod 接入仓库构建／测试入口，包中只含运行所需文件和说明。

常用命令，在仓库根目录运行，使用本机可用的 Python：

```powershell
python mods/<Mod>/tests/run.py
python tools/build.py <Mod>
```

修改共享构建、测试或打包工具时，再运行相关工具测试及受影响的回归。例如：

```powershell
python tools/test.py --skip-native
python -m unittest discover -s tools/tests
```

涉及 C++ 或原生构建的改动还须完成对应编译和原生检查，不能用 `--skip-native` 作为原生验证已通过的证据。离线通过不代表游戏内通过。

## 7. 本地安装和实机验收：必须关闭游戏再更新

**禁止在 Palworld 运行中覆盖 Lua、DLL、PAK 或其他运行资源，禁止通过触碰 `main.lua` 等方式触发热加载。临时探针、修复和探针移除同样遵守。** 本次在竞技场页面打开时热加载后发生无响应，后续统一采用关闭 → 安装 → 完整启动。

### 安装步骤

1. 先判断当前游戏是否有用户未完成的操作，正常退出并确认游戏进程已结束。
2. 记录实际测试环境、相关 mod 和安装文件；备份需要替换的安装以及会受影响的存档／独立数据。
3. 使用 mod 自带安装脚本；安装脚本应在检测到游戏仍运行时拒绝写入。不要绕过这个检查手动复制。
4. 继续使用现有本地开发安装方式。只有准备 Workshop 发布时才切换到对应 Workshop 目录，遵循 [Workshop 约定](WORKSHOP.md)，保留既有 PublishedId、`.workshop.json` 和包布局。
5. 核对安装文件与源码／构建产物一致，确认没有新旧版本同时加载；完整启动游戏并查看日志。

### 存档隔离

涉及发奖、消耗、积分或进度的试验优先使用独立存档副本。确认原存档已保存且游戏关闭，再复制；测试世界要有独立世界标识，mod 数据也必须对应测试身份。

记录原存档相关文件的哈希作为基线。不能把一个假定世界长期称为“用户原存档”；实际测试前确认正在加载的世界。用户自己游戏后文件变化不能擅自回滚。

不要为测试清空真实玩家额度、修改真实积分或批量领奖。只在明确隔离的测试世界操作其数据。结束后先退出游戏，再归档自己创建的副本和对应测试记录；保留用户自行创建的世界。递归移动前校验绝对路径和精确目标。

### 实机矩阵

按功能选择适用项，至少覆盖正常路径及本次变化直接影响的边界：

| 场景 | 核对内容 |
| --- | --- |
| 冷启动、第一次打开 | 加载成功；入口位置、层级、数量、语言正确 |
| 未解锁、部分解锁、全部解锁 | 正常显示；不能越过解锁结算；无白块或焦点丢失 |
| 有额度、最后一次、零额度 | 次数正确；零次重复点击无额外奖励；界面仍可返回 |
| 不同难度／选项 | 结算对应当前选择；共享／独立资源符合需求 |
| 正常领取、快速双击 | 库存、积分、消耗前后差值准确，不重复执行 |
| 动画期间继续操作、返回、再次打开 | 实际反馈正确；不抢输入；不残留控件或绑定 |
| 背包满、数据异常、权限不满足 | 明确失败反馈，无免费重试或重复发奖 |
| 跨天、升级、退出后重进 | 刷新、补差、保存符合设计，不凭空重置 |
| 原版入口、相关其他 mod | 原有交互和结算仍正常，无额外进入战斗等副作用 |

不能只拿“全解锁的高段位存档”作为全部 UI 状态验收。Better Arena 的白块就出现在部分通关状态，之前全通关测试没有覆盖到。

实际看画面、操作真实入口，结合日志和结算前后数值核对。Windows 窗口操作按 computer-use 技能执行；API 调用或委托广播验证应标为接口／路由测试，不能冒充鼠标、键盘或手柄已实测。

## 8. 异常恢复和证据记录

出现白块、卡死、重复结算或存档异常时，先捕获当前画面、进程响应和最近日志，保留证据；不要继续向卡住的进程注入脚本或反复触发同一操作。

尝试正常退出。无法退出且需要恢复时，先备份当前磁盘上的存档和独立记录，再按已有授权结束卡住的进程、离线修复并完整重启。备份磁盘文件不等于已保存内存中的最新进度，不宣称强制退出一定无损。

在 `mods/<Mod>/docs/VALIDATION.md` 或该 mod 既有验收文档记录：

- 游戏／加载器版本、测试环境、实际支持范围。
- 哪些是离线测试、接口测试、真实 UI 实测或用户确认。
- 关键前后数值、截图／日志的本地位置、失败现象、修复和复测结果。
- 未验证场景和限制；早期版本的验收不能冒充最终版本的覆盖。

没有线程栈等证据时，不把“重载阶段卡住”直接写成已查明的具体死锁原因。用户确认“现在可以了”可以记录为用户验收，不能补写为未执行过的自动化测试。

## 9. 清理、提交和交付

交付前检查实际安装和发行包都来自最终源码。移除探针、临时命令入口和测试配置也须在游戏退出后安装；需要继续使用时完整重启，确认进程响应和加载日志。

README 说明最终行为、依赖、配置、数据位置和当前限制；构建入口、测试入口、包内容和验收记录保持一致。发布 Workshop 时另按 [Workshop 文档](WORKSHOP.md) 处理本地化说明和生成列表。

只有用户要求提交／推送时才执行 Git 提交／推送；不自行创建分支或 PR。按根 `AGENTS.md` 使用当前分支和 Conventional Commits，明确暂存本次文件，不顺手加入无关修改、外部工具、存档或生成包。

交付时简要说明改了什么、装到了哪里、哪些检查已通过和哪些仍未验证。未实际启动不能说“已重启”，未实际复测不能说“已修复并验证”。

## 完成条件

- 最终用户流程及反馈完整，原版相关路径保持正常。
- 相关离线检查通过，安装文件和最终构建一致。
- 按适用矩阵完成实机复核；尚未验证项有明确记录。
- 临时入口和自建测试副本已妥善清理，持久数据与用户存档不被测试混用。
- 安装遵守关闭游戏后更新；用户要求的提交、推送或发布已完成且可核对。
