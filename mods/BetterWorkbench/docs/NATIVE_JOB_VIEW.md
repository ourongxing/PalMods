# 原生任务材料视图接入依据

2026-10-06，本机构建的静态分析。所有地址均为 RVA，不能用于其他游戏版本。当前游戏只读桥接没有修改制作行为。地址扫描工具为 `tools/inspect_craft_calls.py`；它从 PE unwind 的函数起点解码，确认候选位置是实际 call 指令。反编译原始输出保存在 `.tools`，不作为可编译的函数签名。

## 有效数量表与有效需求列表是两个原生函数

`0x2fad860` 重新从原配方取得材料，调用原生修正项 0x5b，对数量进行游戏自身的整数取整，然后合并到材料数量表。它没有调用已安装桥接的 `0x2fadaa0`。仅 Hook 后者不会覆盖每完成一件时的消耗。

数量表函数的公开 exec 包装位于 `0x2981460`，调用位置为 `0x29815d0`。完成流程调用现场在 `0x3012e7a`：RCX 和 RDX 都是当前模型，R8 是配方 ID，R9 是栈上的数量表对象。反编译器列出的额外参数没有在这一调用现场得到证实，不能直接采用其九参数伪代码签名。数量表内部包含稀疏存储和散列状态，不能按普通材料数组读取。

## 整批材料与逐件材料不能混用

例如请求三个电池，库存只有一个碳纤维，其他碳纤维通过煤炭配方展开：整批会使用碳纤维 1、煤炭 4、喷火器官 2，以及原生计算的电池其他投入。这里的 1、4、2 无法同时表示为整数单件需求乘以 3。

因此整批投入应在原版批量乘法之后、库存校验之前接入。每件完成时则使用该件对应的材料数量表。不能把总材料数量直接写入单件需求，也不能用除法、舍入或重新应用研究系数来适配原版乘法。已持有中间件必须优先使用，不能为了凑出均匀单件需求而忽略它们。

## 下一项接入要求

任务需要持有自己的槽位材料顺序、整批实际投入以及逐件消耗顺序；三者应由同一计划生成，原生修正后的需求作为输入。GetCurrentRecipe 返回值的修改只作用于这一任务的副本，产品 ID、产量、工作量和全局配方表保持原版数据。补料缺口与可工作判断需要看到同一剩余计划。任务保存、读档和任务结束时的清理也必须有对应记录，不能仅依赖运行中 UObject 指针索引的临时表。

在接通这些路径前，穿透继续关闭。下一步先核对整批库存校验后的输入参数和任务保存字段，再实现任务视图；不会先部署仅修改单件需求的版本。

## 保存字段与逐件计划实现进展

通过 `UPalMapObjectConvertItemModel::SerializeProperties` 字符串的 RIP 相对引用，定位到函数 `0x301ff70`。该函数先调用基类相关路径 `0x301fe80`，再进入模型自己的 archive 区段。已观察到它处理模型 +0x290 的配方 ID、+0x29c 的剩余数、+0x298 的请求数、+0x2b8 的浮点字段以及 +0x319 的布尔字段。浮点／布尔字段的语义和基类保存内容仍需核对，不能改写其布局或宣称已找到自定义数据扩展口。

新增纯逻辑 `BatchSchedule.resolve`：为每次根配方执行取得成本提供器返回的有效需求，沿用 RecipeResolver 的工作台限制、配方选择和库存优先规则，在整批内共享虚拟中间件余量。返回独立的每件实际投入、整批实际投入以及最多五类的槽位身份列表；不会用整批投入除以件数、重新计算研究系数或给世界库存添加虚拟余量。计划是准备数据，尚未连接到游戏的库存校验或材料数量表。

离线验证包括：三个电池只有一个现存碳纤维时，第一件使用现存碳纤维、后两件展开；中间配方一次输出两件时下一根配方共享余量而不扣虚构中间件；超过五类输入或批量上限时拒绝；木炭不能跨炉子展开。49 项测试通过，原有 200 个守恒场景保留。部分完成后的剩余材料统计仅为接入验证参考，实际取消仍需原生返还，未启用自定义退款。

## 整批校验入口的只读桥接

原版 worker 在 `0x30061ec` 调用库存计数函数 `0x2fa0020`。RCX 为模型上下文，RDX 为原版收集的容器引用数组，R8 为材料名称数组，R9 为计数输出数组。它从这些容器汇总匹配物品数量，返回 12 字节名称／数量条目。该函数末尾释放 R8 指向数组的数据分配；此参数表现为按值传递数组的消耗，不能在调用后读取或传入 C++ vector 的内存供它释放。

worker 调用前的 RSP+0x58 是已完成批量乘法的需求数组，RSP+0x40 是为计数函数准备的名称数组。版本 0.2 桥接仅在已验证调用位置读取前者，在原函数调用前复制后者的名称，并在调用后复制返回计数。它将整批需求和原版库存范围结果关联到同一次请求。读取栈位置前要求游戏构建、函数入口、批量乘法指令窗口和调用窗口全部匹配；指针不跨回调保存。

版本 0.2 已部署并实机确认碳纤维×3：原生库存范围 Coal=3151、FireOrgan=56，整批需求 Coal=6、FireOrgan=3。随后 Computer×3 是电脑请求，不能记作电池实测。不合并 Lua 的背包／基地计数，不修改材料、容器或配方。

## 0.3 快照和任务计划候选版

新增同步 worker 作用域，读取当前工作台、焦点原始配方、原生成本和额外材料的原生库存查询，返回独立字符串／数字数据。名称查询数组用 FMemory 分配并由原生计数函数消费；新结果复制后释放。原请求参数及结果不变。队列不保存 UObject、FName 索引或 Lua 状态。完整查询中未返回的已请求 ID 是原生槽遍历没有发现匹配材料，可记为 0，不能把这一结论用于失败或部分查询。

NativeSnapshotPlan 用这份数据驱动 BatchSchedule。根配方整批需求须与同次原生有效成本相符，否则拒绝规划。焦点成本提供器仅支持单次执行，避免引入未验证的批量公式。缺煤时可尝试已有木炭，木炭生产仍受当前工作台限制。计划 ReadOnly=true，科技及权限未确认，EligibilityVerified=false。

JobPlan 提供逐件材料表、槽位顺序、剩余实际投入和纯数据保存载荷。只有成功原生事务后的进度、输入与计划一致才允许推进一件；恢复要求世界、工作台、任务、构建和存档检查点全部匹配，且合计、槽位和实际输入一致。它未读写原生存档；独立 sidecar 不能证明与游戏存档原子一致，当前不会据此开启制作写入。

57 项 Lua 测试、1,414 条本机配方校验、原生副本隔离测试通过，0.3 DLL 的 46 个导入接口匹配运行库。0.3 已于 14:42 部署，14:42:49 启动日志确认快照 API 和三个原生读取通道安装成功；具体制作快照待确认。任务材料写入、消耗数量表和原生存档扩展尚未启用。

## 原生科技判断和任务身份入口

进一步反编译已将 `IsDeniedRecipe` 的 exec 0x2ab90e0 与 native 0x31cc070 对应：它查询当前数据对象的配方禁用数组，不能当成科技已解锁。worker 的早期请求过滤调用了它。`IsUnlockCraftRecipe` 的 exec 0x2b21fd0 调用 0x326aa30，以配方 FName 地址作为参数并写回布尔结果；`IsUnlockRecipeTechnology` 的 exec 0x2b22080 调用 0x326ac80。后续可复用这些原生方法，但必须先确认数据对象属于这次请求的玩家，不能把研究成本所用的数据对象或 CDO 代替玩家科技数据。

`GetRecipes` exec 0x29b8820 调用 0x300dde0，后者更新／返回模型 +0x2a8 的缓存数组，不能仅凭名单存在推断科技已解锁。`GetModelInstanceId` exec 0x29b8790 将模型 +0xb0 的 16 字节身份复制到返回值；该身份入口可用于绑定工作台，世界身份、任务代次及同一原生存档检查点仍需对应来源。上述静态结论尚未成为新的游戏调用或写入功能。
